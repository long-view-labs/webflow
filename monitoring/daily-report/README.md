# Nourish daily report

One run a day: a visual + page-health check of 43 pages (desktop 1440×1000 and mobile 390×844: every main-nav page plus one page per template in `pages/core.json`, every paid page in `pages/paid.json`, every ad landing page in `pages/landing.json`), a nav/menu check, a quiz and insurance-search check, Lighthouse lab scores for every page (median of 3 loads, analytics blocked and verified), per-page Amplitude numbers, a tracking-stability summary, and one detail page per page. The result is posted through the shared sender in `../alerts.js` as a compact Slack message (quiet on no-change days, see below) linking to the full HTML report at https://nourish-web-report.pages.dev/ (Cloudflare Pages project `nourish-web-report`, noindex header + robots.txt, HTML and images only; `publish.mjs` refuses to publish if a local path is in the HTML, and `daily.mjs` does not publish at all unless the speed test proved it reached no analytics). The local copy is `monitoring-local/daily-report/latest/index.html`; the message links to it if the report was not published. The page has no login: anyone with the link can see it.

## What runs

- **Pages** – the Unify page checker (`~/Documents/Codex/2026-10-27/task/unify-page-checker`, override with `NOURISH_PAGE_CHECKER_DIR`) is used as-is: BackstopJS/Playwright capture with motion frozen, independent health checks, a same-run repeat capture as a noise check, and a comparison with the previous run's screenshots. Pages are listed in `pages/*.json` (the checker allows 25 per file).
- **Flagging** – same rules as Unify. Issues are only real breakage: HTTP errors, uncaught page errors, broken first-party assets, missing required content (h1 by default; signup links on the paid pages; headline and insurance form on `/does-my-insurance-cover-nutrition`, which has no h1), metadata (title, canonical, unexpected noindex) and failed nav/menu checks. A visual change is more than 2% of pixels vs the previous run. Accessibility is reference only. One comparison mask: the partner hero image (`.condition-hero_image`), whose `srcset` lists the same file at 500w and 1236w so Chrome renders it at a different size from load to load (5–8% drift); the health check still fails if it doesn't load. Every capture also hides the OneTrust cookie banner (`finalStateCss` in each page set): it appears 0.3–0.8 s after load, so a capture landing before it read as a ~12% change (Oct 29 2026). An issue already present in the previous run shows as "still open" and doesn't turn the DM red again.
- **Quiz and insurance search** (`form-check.mjs`) – on every page state: answers each step of the Videsigns quiz and checks it ends on the signup link; in each insurance-search module (hero "Check your coverage", "Find dietitians") picks Cigna, California and a first name where present and checks the module's own signup link keeps its attribution and gains `state`, never carries the private prefill (`nourishPayerId`, `firstName`; kept off the DOM since v2.623.7 so analytics and pixels can't see them), and that clicking it opens signup with `nourishPayerId`, `state` and `firstName`. The click is captured by a page-level route above `protectPage`'s and aborted, so signup never loads (before Oct 29 2026 the quiz's signup click slipped past the context-level capture and loaded signup with its events dropped). Signup navigations are captured and aborted. The quiz library's own setup self-check throws on every load (it looks for `data-form="multistep"`; the form uses `multi-step`); that one error is listed as known, not an issue, only where the form check traces it to the Videsigns script on that page state.
- **Console and network** (`console-check.mjs`, Oct 29 2026) – on every page state, one more load with the same protection as the nav and form checks and 3 s idle: `console.error` lines, any response of 400+ and any failed request, from any host, plus the `data-businessunit-id` of every `.trustpilot-widget` (must be `69cd80f7c278f2faf5031ff2`; the retired `6480f128811d0a0b3ba2b211` left ~80 pages with blank widgets until Oct 29 2026, trustbox-data answering 400). Not counted: requests the check itself blocked or made unresolvable, browser-cancelled requests (`ERR_ABORTED`), console lines that only repeat a failed request or name a URL the check blocked (RudderStack's "Failed to deliver", Statsig's networking errors), and the entries in `CONSOLE_NOISE` (multi-step.js's usage counter POST), each with its reason. A widget API (`widget.trustpilot.com`) failing is always an issue. Findings join the page's health result (failed files, page errors), so they get the usual new / still-open handling and show on the cards; the main report has a cross-site "Console and network" section and each detail page a per-viewport table. Uncaught page errors stay with the checker's own health check. Fire drill (real browser, Trustpilot's real bootstrap, page served locally under a www.nourish.com address): `node --test tests/console-check.browser.mjs`.
- **Search indexing** (`seo-check.mjs`, Oct 29 2026) – plain GETs, no browser and no JavaScript: `sitemap.xml`, every URL in it (1,421 on Oct 29 2026), the static pages it leaves out (`pages/static-paths.txt`, from the Webflow Pages list; add new static pages and variants there) and the report's own pages; about 4 minutes at 8 at a time. Issues: a sitemap URL that serves noindex (meta robots/googlebot or `X-Robots-Tag`), an ad-only or variant page that is indexable (`AD_PATTERNS`: `/paid*`, `/landing-pages/*`, `/landing-page/*`, `/landing/*`, `/lp-*`, `-b`/`-c` variants outside the blog, `/dev/*`, `/wip/*`, `/forbes`, `/money-saving-mom`, the employer pages, `/nutrition-program`, `/condition/glp-1s`) and a Trustpilot widget with another business-unit id anywhere on the site. To review, not issues: sitemap URLs that redirect or error. Indexable on purpose: `/quiz/*`, `/gut-health-quiz`, `/signup/weight-loss`, `/refer`, `/refer-a-friend`. Known and shown once as a group, never alerted (`KNOWN`): noindex CMS items under `/landing-page/`, `/landing/` and `/partners/` still in the sitemap (Webflow has no sitemap toggle for CMS templates), and the indexable `/partnerships/nourish-modify-*` CMS pages (open item). New issues turn the day red and get an "Indexing" line in Slack; ones already open the day before get a review line. The paid and `/landing-pages/` report pages are marked `expectNoindex` (set noindex Oct 29 2026), so their noindex is not a health finding.
- **Nav** (`nav-check.mjs`) – main template: nav links visible and the Company dropdown opens; partner template: hamburger opens on mobile; paid/landing template: nav bar shows its link/button.
- **Performance** (`performance.mjs`) – after the page work, Lighthouse on every page in the three page sets on desktop and mobile, each loaded 3 times (`NOURISH_PERF_RUNS`) with the median kept (`medianRun`: scores, LCP, CLS, TBT; the day's spread is shown on the card), because single loads on this site move 10+ points (258 loads, about 10 s each), scoring Performance, Accessibility, Best practices and SEO through the page checker's wrapper (`src/performance.mjs`: the `bf-cache` audit is skipped because its unblocked re-navigation leaked pageviews on Unify on Oct 27 2026). Analytics are blocked at the Chrome level: the checker's analytics hosts plus Nourish's own are unresolvable (`--host-resolver-rules`): RudderStack's SDK at `jssdk-proxy.{usenourish.com,nourish.com}` and its collector at `dataplane-proxy.{usenourish.com,nourish.com}`, the Statsig experiment sidecar's endpoints (`featureassets.org`, `api.statsigcdn.com`, `prodregistryv2.org`, `statsigapi.net`, and `cloudflare-dns.com`, which its SDK uses to look up fallback domains when those fail), read from the live pages on Oct 29 2026, plus Intercom (its messenger ping registers a visitor session), Cloudflare Web Analytics, Sentry (all three answered in the first lab run), Axiom and the Lambda function URL that `/become-a-dietitian` uses as a self-hosted Statsig proxy (both answered in the re-check), the LinkedIn insight hosts, TikTok and GTM. This wider list is for Lighthouse only, which has no request routing; the capture, repeat, nav and form browsers all use the checker's own options, so the page under test is the same page that was captured. Each load's own network log is then checked for answered requests to any of those hosts; the count is stored per load (`report.json` → `performance.rows[].analyticsRequests`). Scores, LCP, CLS and total blocking time are drawn as donut gauges on each page's detail page; the main report keeps one Performance line. The only Performance alert: a page's **Performance** score drops by more than 10 points against the previous run (same page and viewport), or a load reached an analytics host; the other three categories never alert. A day whose loads reached analytics is discarded as the next day's baseline. Lab numbers are medians of throttled loads on this Mac, so a few points of day-to-day movement is still normal. A leak in any of a page's loads counts; a load that threw before writing a network log is ignored when another load of that page is verified. The HTML Lighthouse reports are not saved (only HTML is published); the JSON stays in the run folder. Budget: `NOURISH_PERF_BUDGET_SECONDS` (default 3600); pages past it are recorded as skipped.
- **Page cards** (`render.mjs` + `page-metrics.mjs`) – each card in the main report shows, under its states table, one Amplitude line: page views, Get Started clicks (and their share of views) over the last 7 days, and the share of people who clicked Get Started on that page and reached FlowLoaded within a day. Lighthouse scores and lab vitals are on the detail pages only (Gemin, Oct 29 2026).
- **Per-page Amplitude** (`page-analytics.mjs`) – modelled on the checker's per-page PostHog fetch for Unify: `Viewed Page` grouped by `path` and `Get Started Clicked` grouped by `location` (one segmentation query each, 30 Pacific days ending yesterday; `page_path` is missing on about a third of clicks, so it isn't used), plus one funnel per page that had clicks (Get Started Clicked on that path → FlowLoaded, 24 h window, last 7 days). Read-only Dashboard REST API with the same Keychain item as the volumes (`nourish-amplitude-api`); without it the cards and detail pages say the numbers are unavailable and the run carries on. Counts only. These numbers sit inside the analytics markers, so the published copy drops them (one note per page) unless site-audit `config/daily.json` sets `nourish.publishAnalytics`; the local copy always has them.
- **Detail pages** (`detail-page.mjs`) – `pages/<id>.html` per page, linked from each page card ("Details and analytics →"): captured states, health findings, the nav and quiz/insurance-search results, the Lighthouse gauges with metrics, a 7-day strip of the Performance score from the stored runs (`loadScoreHistory` in the checker; a day whose speed test reached analytics is skipped), and Amplitude charts: page views and Get Started clicks per day for 30 days and the click → FlowLoaded funnel (private, as above).
- **Real-user Core Web Vitals** (`crux.mjs`, Oct 29 2026) – the 75th-percentile LCP, INP, CLS, FCP and TTFB of real Chrome visits over 28 days, mobile and desktop, from Google's Chrome UX Report API, shown on each detail page after the lab scores and coloured by Google's thresholds. CrUX reads Chrome's own dataset, so nothing loads the page and no tracking fires. A page with too little Chrome traffic shows the whole site's numbers, labelled as such. Needs a Google Cloud API key with the Chrome UX Report API enabled: the Keychain item `nourish-crux-api` if present, otherwise the Google key already stored for Unify's PageSpeed Insights (`unify-psi-api`, account `unify`); that key works only if the Chrome UX Report API is also enabled on its Cloud project. Without either, the section says so. **Why not PageSpeed Insights:** every PSI call runs a Lighthouse load of the live page from Google's servers with nothing blocked, so it fires RudderStack, GTM and the vendor tags and adds Viewed Page events to Amplitude (Unify's PostHog audit saw exactly that). The lab scores move to PSI only once Nourish has a lab-flag guard like the one being built for Unify (tags skipped when the URL carries the flag), live and proven not to change tracking counts.
- **Tracking** (`tracking.mjs`) – reads the hourly monitor's latest results in `monitoring-local/` (never re-runs it) and, when an Amplitude key is present, compares yesterday's volumes for `Viewed Page`, `Viewed  Page` (two spaces), `Get Started Clicked`, `FlowLoaded`, `MarketingSignUpCompleted` and `Get Started Clicked` with `cta_name` containing `| Other` (should be 0) against the same weekday last week and the trailing 7-day average.

- **GA4 and Search Console** (`google.mjs`) – read through NewBase's adapters (`~/ShipStudio/newbase/console/src/server/sources/`: `google.ts` service-account JWT with read-only `analytics.readonly` + `webmasters.readonly` scopes, `ga4.ts`, `search-console.ts`), imported as-is (`NEWBASE_DIR` overrides the path). GA4: yesterday's sessions, users and key events vs the same weekday over the previous 4 weeks, plus top pages (by sessions) and channels. Search Console: the latest final day (2–3 days behind) vs the 7 days before for clicks, impressions, CTR and average position, plus top queries and pages, per site in `google-sources.json`. Same flag thresholds as the Amplitude volumes; CTR and position are reported, not flagged. Top queries and pages appear on the published (noindex, no-login) page.

## Safety

- Every browser uses the page checker's protection: analytics hosts (RudderStack, Amplitude, GA, Meta, Bing, LinkedIn, Clarity, …) are unresolvable, all non-GET requests are aborted and `sendBeacon` is a no-op. The Lighthouse Chrome adds Nourish's own hosts (`performance.mjs` → `NOURISH_ANALYTICS_HOSTS`: the RudderStack SDK and dataplane proxies on both apexes, the Statsig endpoints and their DNS-over-HTTPS fallback, Intercom, Cloudflare Web Analytics, Sentry, Axiom, the Lambda Statsig proxy, LinkedIn, TikTok, GTM). Canny's and Tolstoy's widget scripts still load; neither sent anything in the checks. The nav check also aborts `/dietitian-application` and the RudderStack dataplane proxy. A probe of `/paid` on Oct 27 2026 showed no analytics request completing. The Lighthouse run has no request routing, so it relies on the unresolvable hosts and proves the result from its network log: the report is published only when every attempted load shows 0 answered analytics requests (a load that threw before writing a log is unverified and also blocks publishing that day; the message says why). Nothing is clicked except menu toggles; no forms are submitted.
- `/dietitian-application` is not in the page list and is never loaded in a browser. The indexing check may GET its HTML (no JavaScript runs, so no draft is created), like curl.
- Credentials stay in the login Keychain: `nourish-monitor-slack` (Slack bot token, already used by the hourly monitor) and `nourish-amplitude-api` (account = Amplitude API key, password = secret key). Nothing secret is read from or written to the repo.

## Commands

```bash
node monitoring/daily-report/daily.mjs --now --no-slack
```

`--now` runs even if today's run already completed; `--no-slack` prints the message instead of sending it, with a line saying whether it would have posted; `--no-publish` skips the Pages update. Republish the latest report alone with `node monitoring/daily-report/publish.mjs`. Results: `monitoring-local/daily-report/runs/<time>/` (last 30 kept), `latest` symlink, `state.json` (which also records the last message's status for the quiet rule). A run takes about 85 minutes (20 for the pages, 10 for the console check, 45 for Lighthouse, 4 for indexing); `daily.mjs` allows 150.

## Slack message (Oct 29 2026)

Same shape as Unify's compact message (`summary.mjs` → `dailyNotification` for the contract-v1 model, `renderDailyMessage` for the text):

1. headline: status emoji, "Nourish daily site check — <no change | review needed | site problem | check failed | incomplete>", run time in Pacific
2. one line of numbers: pages captured (desktop + mobile), visual changes, new issues, quiz and insurance search working
3. attention lines only when present: pages not captured, changed pages and new issues (up to 4 ids, then "+N more"), still-open issues from before, run problems and unknowns (⚠️), and the supporting areas
4. the report link (or the local path when the report was not published)
5. a one-line next step, omitted when nothing changed

The headline is the page check (visual, health, nav, quiz and insurance search) and whether the run finished. Supporting areas add a line only when they need attention, and a red one posts on its own without changing the headline: 🔴 *Performance* (score drop of more than 10 points, or the speed test reached analytics), 🔴 *Hourly tracking monitor* (no results or stale; its own failures are alerted by the monitor itself and are not repeated here), 🔴/🟡 *Amplitude* (a flagged event volume; a missing Amplitude key is shown in the report, not here), plus SEO/AEO, GA4 and GSC lines when site-audit turns them on and they are not green. The weekly site-audit Performance line is no longer shown anywhere; today's Lighthouse result replaces it in the report's summary table too.

**Quiet rule:** the channel hears about a day only when the headline is not "no change" or a red supporting line is present, or once after such a day so the clear is seen (`state.json` → `lastNotification.neededAttention`). Still-open issues from an earlier day do not post by themselves; they appear as a ⏳ line when something else does. With no record of the previous day the sender stays quiet.

```

```

Set up GA4 and Search Console access (read-only; skipped cleanly until done):

1. Google Cloud console: in a project you own, enable the **Google Analytics Data API** and the **Google Search Console API**, create a service account (no roles needed), and download a JSON key for it.
2. GA4: Admin → Property access management → add the service account's email as **Viewer**. Note the numeric **Property ID** (Admin → Property details) and put it in `google-sources.json` as `ga4Property`.
3. Search Console: for `sc-domain:nourish.com` and the old usenourish.com property, Settings → Users and permissions → add the email with **Restricted** permission. If the old property is a URL-prefix one, change its entry in `google-sources.json` to that URL (e.g. `https://www.usenourish.com/`).
4. Store the key in Keychain, then delete the downloaded file:

```bash
security add-generic-password -s nourish-google-sa -a nourish-daily-report -w "$(jq -c . ~/Downloads/KEY_FILE.json)" && rm ~/Downloads/KEY_FILE.json
```
